# Conversations Specification

## Purpose

Persistent web chat threads: the user creates, renames and deletes conversations, sends
messages, and receives assistant replies generated by server-owned runs that survive browser
disconnects and are recoverable after restarts.

## Requirements

### Requirement: Thread management

The system SHALL let the user list, create, open, rename and delete threads through
`/api/threads`. The list SHALL be ordered by newest activity first. Thread detail SHALL include
the full saved message history (no pagination) and the latest run, or `null`.

#### Scenario: New thread title

- **WHEN** a thread is created
- **THEN** its title is `New conversation` until the first prompt replaces it with that prompt's
  first 80 normalized characters

#### Scenario: Rename validation

- **WHEN** a rename request has an empty title or one longer than 200 characters
- **THEN** the response is `400` with `{"error": ...}`

#### Scenario: Missing thread

- **WHEN** any thread endpoint references an unknown thread id
- **THEN** the response is `404`

#### Scenario: Delete thread

- **WHEN** a thread with no running run is deleted
- **THEN** the thread, its messages and runs are removed and the response is `{"deleted": true}`

### Requirement: Sending a message starts a server-owned run

Sending `{"text": ..., "attachment_ids": [...]}` SHALL commit the user message, its attachment
references and a new `running` run atomically and return `202` with the run. `attachment_ids` is
optional (at most 5 ids of uploads not yet sent); text MAY be empty when at least one attachment
is present. Generation SHALL continue independently of any browser connection; closing the
browser SHALL NOT cancel it. On success the new messages and `completed` status SHALL be
committed together.

#### Scenario: Message accepted

- **WHEN** the user sends a non-empty message of at most 1,000,000 characters to an idle thread
- **THEN** the response is `202` with a run whose status is `running`

#### Scenario: Attachment-only message accepted

- **WHEN** the user sends empty text with one uploaded PDF to an idle thread
- **THEN** the response is `202` and the saved message shows the PDF

#### Scenario: Invalid message

- **WHEN** the message is malformed, longer than 1,000,000 characters, or has empty text and no
  attachments
- **THEN** the response is `400` and nothing is saved

#### Scenario: Invalid attachment reference

- **WHEN** a message references an unknown attachment id, one already sent, or more than 5 ids
- **THEN** the response is `400` and nothing is saved

#### Scenario: Concurrent run blocked

- **WHEN** a send, retry or delete targets a thread whose latest run is still running
- **THEN** the response is `409`

### Requirement: Failed and interrupted runs

A run that errors SHALL become `failed`; a run cut off by shutdown or found unfinished at startup
SHALL become `interrupted`. In both cases the saved prompt SHALL be retained and partial
generated output SHALL NOT be saved. Recovery SHALL never resubmit automatically.

#### Scenario: Startup recovery

- **WHEN** the server starts and a run is still marked `running`
- **THEN** the run becomes `interrupted` and the prompt remains in the thread

### Requirement: Manual retry

Retry SHALL create a new run for the latest failed or interrupted prompt without duplicating
the user message.

#### Scenario: Retry an interrupted prompt

- **WHEN** the latest run is `interrupted` and the user retries
- **THEN** the response is `202` with a new running run and the thread still holds one copy of the prompt

#### Scenario: Nothing to retry

- **WHEN** the latest run is `completed` or there is no run
- **THEN** retry returns `409`

### Requirement: Bounded conversation history

Each turn SHALL include the newest complete earlier turns of the thread that fit the configured
history budget (`CONVERSATION_HISTORY_BUDGET`, default 64,000 characters); turns that do not fit
are omitted whole, never split.

#### Scenario: Long thread

- **WHEN** a thread's history exceeds the budget
- **THEN** the oldest turns are omitted from the model request while remaining saved and visible in the UI

### Requirement: Shareable selection and display

The UI SHALL record the selected thread in `?thread=<id>` so it can be reopened in another
browser, SHALL display saved timestamps in the browser's locale and time zone, and SHALL clear
the selection when the selected thread no longer exists. Rejected sends SHALL restore the
composer draft.

#### Scenario: Open shared link

- **WHEN** a browser opens `/?thread=<id>` for an existing thread
- **THEN** that conversation is selected and displayed
