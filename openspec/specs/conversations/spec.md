# Conversations Specification

## Purpose

Persistent web chat threads: the user creates, renames and deletes conversations, sends
messages, and receives assistant replies generated by server-owned runs that survive browser
disconnects and are recoverable after restarts.

## Requirements

### Requirement: Thread management

The system SHALL let the user list, create, open, rename and delete threads through
`/api/threads`. The list SHALL be ordered by newest activity first. Thread detail SHALL include
the full saved message history (no pagination) and the latest run, or `null`.

#### Scenario: New thread title

- **WHEN** a thread is created
- **THEN** its title is `New conversation` until the first prompt replaces it with that prompt's
  first 80 normalized characters

#### Scenario: Rename validation

- **WHEN** a rename request has an empty title or one longer than 200 characters
- **THEN** the response is `400` with `{"error": ...}`

#### Scenario: Missing thread

- **WHEN** any thread endpoint references an unknown thread id
- **THEN** the response is `404`

#### Scenario: Delete thread

- **WHEN** a thread with no running run is deleted
- **THEN** the thread, its messages and runs are removed and the response is `{"deleted": true}`

### Requirement: Sending a message starts a server-owned run

Sending a message SHALL commit the user message, its attachment references and a new `running`
run atomically and return `202` with the run. Generation SHALL continue independently of any
browser connection; closing the browser SHALL NOT cancel it. On success the new messages and
`completed` status SHALL be committed together.

#### Scenario: Message accepted

- **WHEN** the user sends a non-empty message of at most 1,000,000 characters to an idle thread
- **THEN** the response is `202` with a run whose status is `running`

#### Scenario: Concurrent run blocked

- **WHEN** a send, retry or delete targets a thread whose latest run is still running
- **THEN** the response is `409`

### Requirement: Message request body

A message SHALL be sent as `{"text": ..., "attachment_ids": [...], "model": ...}`.
`attachment_ids` is optional (at most 5 ids of uploads not yet sent); text MAY be empty when at
least one attachment is present. `model` is optional and SHALL be a selectable model; when it is
omitted the run uses the thread's current model.

#### Scenario: Attachment-only message accepted

- **WHEN** the user sends empty text with one uploaded PDF to an idle thread
- **THEN** the response is `202` and the saved message shows the PDF

#### Scenario: Invalid message

- **WHEN** the message is malformed, longer than 1,000,000 characters, or has empty text and no
  attachments
- **THEN** the response is `400` and nothing is saved

#### Scenario: Invalid attachment reference

- **WHEN** a message references an unknown attachment id, one already sent, or more than 5 ids
- **THEN** the response is `400` and nothing is saved

#### Scenario: Unknown model on send

- **WHEN** a message names a model that is not selectable
- **THEN** the response is `400` and nothing is saved

### Requirement: Failed and interrupted runs

A run that errors SHALL become `failed`; a run cut off by shutdown or found unfinished at startup
SHALL become `interrupted`. In both cases the saved prompt SHALL be retained and partial
generated output SHALL NOT be saved. Recovery SHALL never resubmit automatically.

#### Scenario: Startup recovery

- **WHEN** the server starts and a run is still marked `running`
- **THEN** the run becomes `interrupted` and the prompt remains in the thread

### Requirement: Manual retry

Retry SHALL create a new run for the latest failed or interrupted prompt without duplicating
the user message.

#### Scenario: Retry an interrupted prompt

- **WHEN** the latest run is `interrupted` and the user retries
- **THEN** the response is `202` with a new running run and the thread still holds one copy of the prompt

#### Scenario: Nothing to retry

- **WHEN** the latest run is `completed` or there is no run
- **THEN** retry returns `409`

### Requirement: Bounded conversation history

Each turn SHALL include the newest complete earlier turns of the thread that fit the configured
history budget (`CONVERSATION_HISTORY_BUDGET`, default 64,000 characters); turns that do not fit
are omitted whole, never split.

#### Scenario: Long thread

- **WHEN** a thread's history exceeds the budget
- **THEN** the oldest turns are omitted from the model request while remaining saved and visible in the UI

### Requirement: Shareable selection and display

The UI SHALL record the selected thread in `?thread=<id>` so it can be reopened in another
browser, SHALL display saved timestamps in the browser's locale and time zone, and SHALL clear
the selection when the selected thread no longer exists. Rejected sends SHALL restore the
composer draft.

#### Scenario: Open shared link

- **WHEN** a browser opens `/?thread=<id>` for an existing thread
- **THEN** that conversation is selected and displayed

### Requirement: Runs record their model

Each run SHALL record the model it runs on and use it for the whole run. Run objects SHALL
include that model, and thread detail SHALL include the thread's current model.

#### Scenario: Run saved before models were recorded

- **WHEN** a thread's latest run was saved before this change
- **THEN** that run's model is `openai:gpt-6.1-sol`, the only model used until then, and the
  thread's current model is `openai:gpt-6.1-sol` while that model is selectable

### Requirement: Retry chooses a model

Retry SHALL accept an optional `model`, which SHALL be a selectable model. When it is omitted,
the retry uses the thread's current model. A failed or interrupted prompt can be retried on a
different model than the one it failed on.

#### Scenario: Retry on another model

- **WHEN** a run on `openai:gpt-6.1-sol` failed and the user retries with model
  `anthropic:claude-opus-5-5`
- **THEN** the new run records `anthropic:claude-opus-5-5` and its reply is generated by that model

#### Scenario: Unknown model on retry

- **WHEN** a retry names a model that is not selectable
- **THEN** the response is `400` and no run is created

### Requirement: Thread model choice

A thread's current model SHALL be the model of its latest run while that model is selectable,
and otherwise the default. A thread SHALL be able to change model between runs; its saved
history SHALL be replayed to the new model like any other turn.

#### Scenario: New thread

- **WHEN** a thread has no runs
- **THEN** its current model is the default

#### Scenario: Remembered choice

- **WHEN** the user sends "how was my threshold session?" with model `anthropic:claude-opus-5-5` and
  later reopens the thread on another device
- **THEN** the thread's current model is `anthropic:claude-opus-5-5`

#### Scenario: Switch mid-thread

- **WHEN** a thread's earlier replies came from `openai:gpt-6.1-sol` and the user sends the next
  message with `anthropic:claude-opus-5-5`
- **THEN** `anthropic:claude-opus-5-5` receives the thread's earlier turns and generates the reply

#### Scenario: Model removed from configuration

- **WHEN** a thread's latest run used a model that is no longer listed after a restart
- **THEN** the thread's current model is the default and the old run still shows its recorded model

### Requirement: Model picker in the composer

When more than one model is selectable, the composer SHALL show a model picker listing the models by
their shown names. It SHALL show the selected thread's current model, or the default for a new
conversation, and SHALL send the shown model with each message and retry. The picker SHALL be
disabled while a response is running. A change that is not sent SHALL NOT be saved. With one
selectable model there SHALL be no picker.

#### Scenario: Pick and send

- **WHEN** the models are `openai:gpt-6.1-sol`, `anthropic:claude-opus-5-5` and
  `anthropic:claude-sonnet-5-5`, and the user chooses `claude-opus-5-5` in the picker and sends
  "plan my easy week"
- **THEN** the run records `anthropic:claude-opus-5-5`, the reply comes from that model, and the
  picker still shows `claude-opus-5-5` after reload

#### Scenario: Unsent change

- **WHEN** the user switches the picker to `claude-opus-5-5`, sends nothing and opens another thread
- **THEN** returning to the first thread shows its saved current model

#### Scenario: Single model

- **WHEN** only the default model is selectable
- **THEN** the composer shows no model picker
